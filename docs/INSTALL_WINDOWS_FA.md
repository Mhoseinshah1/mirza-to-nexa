# راهنمای نصب و اجرا روی ویندوز (نسخه 0.6.0)

برنامه کاملاً **آفلاین** کار می‌کند و فقط روی `127.0.0.1` (همین کامپیوتر) در دسترس است. فایل بکاپ، رمز ZIP و اطلاعات مشتریان به هیچ سرویس اینترنتی ارسال نمی‌شود.

## روش ۱ — فایل اجرایی آماده (پیشنهادی)
1. در GitHub به صفحه **Actions** مخزن `mirza-to-nexa` بروید، آخرین اجرای موفق workflow به نام **CI** را باز کنید و از بخش *Artifacts* فایل `Mirza2Nexa-windows-x64` را دانلود کنید.
2. فایل ZIP دانلودشده را در یک پوشه (مثلاً `C:\Mirza2Nexa`) Extract کنید.
3. فایل `Mirza2Nexa.exe` را اجرا کنید. یک پنجره کنسول باز می‌شود و مرورگر پیش‌فرض صفحه برنامه را باز می‌کند.
   - اگر مرورگر باز نشد، آدرسی را که در کنسول چاپ شده (شامل `?t=...`) در مرورگر وارد کنید.
   - Windows SmartScreen ممکن است به دلیل امضانشدن فایل هشدار دهد: «More info» ← «Run anyway».
4. برای خروج، پنجره کنسول را ببندید. فایل‌های موقت پاک می‌شوند.

## روش ۲ — اجرا از سورس با پایتون
پیش‌نیاز: Python 3.12 یا جدیدتر از python.org (گزینه «Add python.exe to PATH» را فعال کنید).

```powershell
cd C:\path\to\mirza-to-nexa
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install .
mirza2nexa
```

## روش ۳ — ساخت فایل اجرایی روی ویندوز
```powershell
.\.venv\Scripts\Activate.ps1
pip install ".[build]"
pyinstaller --noconfirm --clean packaging\mirza2nexa.spec
python packaging\smoke_test.py dist\Mirza2Nexa\Mirza2Nexa.exe
```
خروجی در پوشه `dist\Mirza2Nexa\` ساخته می‌شود. همین مراحل در CI روی `windows-latest` اجرا و Smoke Test می‌شود.

## مراحل استفاده
1. **بکاپ جدید** ← فایل ZIP بکاپ میرزا را انتخاب کنید (یا بکشید و رها کنید).
2. ساختار ZIP بررسی می‌شود (رمزدار بودن، فایل‌های SQL، فایل‌های نادیده‌گرفته‌شده).
3. رمز ZIP (در صورت وجود)، **واحد پول** و نوع حفاظت بسته را انتخاب کنید:
   - واحد پول: طبق تصمیم مالک NEXA مبالغ میرزا **تومان** هستند. اگر مطمئن نیستید «تعیین‌نشده» را انتخاب کنید؛ بسته ساخته می‌شود اما **مسدود** خواهد بود. هیچ مبلغی خودکار ضرب/تقسیم بر ۱۰ نمی‌شود.
   - حفاظت بسته: «کلید تصادفی جداگانه» (پیشنهادی) یا رمز دلخواه حداقل ۱۲ کاراکتر.
4. **وضعیت تبدیل** پیشرفت واقعی هر مرحله را نشان می‌دهد؛ می‌توانید لغو کنید یا صفحه را ببندید و دوباره باز کنید.
5. **آمار و گزارش**، **صف بررسی** و **پیش‌نمایش خروجی** را بررسی کنید.
6. **دانلود بسته**: فایل `.nxpkg` و فایل کلید `.nxkey` را دانلود کنید و **جداگانه** نگه دارید. کلید فقط در همین نشست در دسترس است.
7. برای مقایسه با بکاپ قبلی، هنگام شروع، عملیات قبلی را در فیلد «مقایسه با» انتخاب کنید (یا در CLI از `--previous-package` استفاده کنید).

## خط فرمان (اختیاری)
```powershell
$env:ZIP_PW = "رمز بکاپ"
mirza2nexa convert backup.zip -o out --money-unit toman --password-env ZIP_PW
mirza2nexa verify out\nexa-migration-XXXX.nxpkg --key-file out\nexa-migration-XXXX.nxkey
mirza2nexa compare old.nxpkg new.nxpkg --old-key-file old.nxkey --new-key-file new.nxkey
```
رمزها از محیط یا ورودی تعاملی خوانده می‌شوند، نه از آرگومان خط فرمان.

## نکات امنیتی
- بسته `.nxpkg` و کلید آن را در یک مکان/پیام ارسال نکنید.
- فایل‌های بکاپ، SQL، رمز و بسته‌ها را هرگز در GitHub قرار ندهید.
- BitLocker را برای دیسک فعال کنید؛ فایل‌های موقت پردازش تا پایان عملیات روی دیسک هستند.
- تا ساخته‌شدن و تست Importer سمت NEXA، این بسته «قابل Import در Production» محسوب نمی‌شود.

## تغییرات نسخه 0.2.0 (فاز ۲)
- همه جدول‌های بکاپ در صفحه «پوشش جدول‌ها» با وضعیت (اجرا شد / آرشیو / نیازمند بررسی / مسدود / بدون داده / غیرقابل انتقال) نمایش داده می‌شوند.
- تاریخچه پرداخت‌ها، تراکنش‌های کیف پول، عملیات سرویس، نمایندگان، تخفیف/ارجاع و پشتیبانی به‌صورت آرشیو فقط‌خواندنی داخل بسته قرار می‌گیرند و هیچ‌کدام روی موجودی یا سرویس اعمال نمی‌شوند.
- گزارش فارسی HTML و فایل CSV پوشش جدول‌ها قابل دانلود است؛ پیش‌نمایش کامل بسته و نسخه قرارداد (1.1.0) قبل از دانلود نمایش داده می‌شود.
- اگر در بکاپ جدول ناشناخته‌ای با داده وجود داشته باشد، بسته «مسدود» می‌شود تا تصمیم آن مستند شود.

## نسخه 0.2.1 (رفع باگ بحرانی)
- در نسخه 0.2.0 فایل EXE ماژول‌های فاز ۲ را شامل نمی‌شد و جدول‌هایی مثل Payment_report و wallet_transaction «بدون طبقه‌بندی» گزارش می‌شدند. این نسخه همه ماژول‌ها را دارد.
- قبل از تبدیل، برای اطمینان از سالم‌بودن نسخه این دستور را اجرا کنید:
  ```powershell
  .\Mirza2Nexa.exe selfcheck
  ```
  خروجی باید `"ok": true` باشد و `"specs"` در نسخه 0.6.0 برابر `53` است (در نسخه 0.3.0 برابر 52 بود). اگر ماژولی کم باشد، برنامه تبدیل را شروع نمی‌کند و خطای `catalogue.incomplete` نشان می‌دهد.
- گزارش هر تبدیل (`report.json`) بخش `catalogue` دارد که فهرست ماژول‌های بارگذاری‌شده را نشان می‌دهد.

## نسخه 0.3.0 (فاز ۳ — آمادگی مهاجرت)
- بخش جدید «آمادگی مهاجرت به NEXA» در منوی برنامه: وضعیت کلی، مالکیت سرویس‌ها، اختلاف تاریخچه کیف پول، پنل‌ها، گروه‌بندی موارد بررسی و فهرست تصمیم‌های لازم مالک.
- فایل‌های `migration-readiness.json` و `migration-readiness.html` (بدون اطلاعات شخصی) از همان صفحه قابل دانلود هستند و نسخه JSON کنار بسته در پوشه خروجی هم نوشته می‌شود.
- نتیجه «آماده» فقط یعنی بسته برای بررسی Importer آماده است؛ تا ساخته‌شدن Importer سمت NEXA، Import عملیاتی ممکن نیست.
- قرارداد بسته به 1.2.0 رسید (فقط افزودنی). دستور `.\Mirza2Nexa.exe schema BACKUP.zip -o schema.json` ساختار جدول‌ها و تعداد ردیف‌ها را بدون هیچ مقداری خروجی می‌دهد.

## نسخه 0.4.0 — بررسی دسته‌جمعی مالکیت سرویس‌ها
پس از تکمیل تبدیل، از منوی «بررسی مالکیت سرویس‌ها»:
1. **فیلتر:** پنل، وضعیت سرویس، علت ابهام، نتیجه بررسی و وضعیت زنده را انتخاب کنید.
2. **انتخاب:** تیک تک‌تک ردیف‌ها، تیک همه ردیف‌های صفحه، یا «انتخاب همه نتایج فیلترشده» (برای هزاران سرویس؛ می‌توانید چند ردیف را دوباره از انتخاب خارج کنید).
3. **پیش‌نمایش:** «تأیید مالک ثبت‌شده در فاکتور» یا «رد و انتقال به قرنطینه» را بزنید. برنامه قبل از هر تغییری تعداد موارد، موارد غیرقابل‌تأیید، ریسک‌ها و نمونه‌هایی را که تک‌تک بررسی نکرده‌اید نشان می‌دهد.
4. **تأیید نهایی:** تعداد دقیق موارد را تایپ کنید و تیک «ریسک‌ها را می‌پذیرم» را بزنید. اگر در این فاصله چیزی تغییر کرده باشد، برنامه اجرا نمی‌کند و پیش‌نمایش تازه می‌خواهد.
5. **بازگرداندن:** هر دسته از بخش «دسته‌های ثبت‌شده» قابل بازگرداندن است، تا وقتی تصمیم‌ها «قفل برای Import نهایی» نشده‌اند.
6. **خروجی:** فایل `ownership-decisions.json` با کلید بسته امضا می‌شود و همراه بسته به Importer داده می‌شود.

نکات مهم:
- «تأیید مدیر» فقط مالک ثبت‌شده در فاکتور میرزا را می‌پذیرد و **اثبات مالکیت نیست**؛ در همه گزارش‌ها جدا از «مالکیت اثبات‌شده» شمرده می‌شود.
- سرویس‌های بدون مالک معتبر یا با تعارض جدی (چند مدعی، انتقال ثبت‌نشده در فاکتور، …) قابل تأیید نیستند و در قرنطینه می‌مانند؛ هیچ مالک دلخواهی تعیین نمی‌شود.
- تصمیم‌ها در پوشه برنامه (`reviews`) ذخیره می‌شوند و با بستن برنامه از بین نمی‌روند؛ اگر همان بکاپ را دوباره تبدیل کنید، تصمیم‌ها برمی‌گردند. شناسه تلگرام یا نام کاربری در این فایل ذخیره نمی‌شود. در یادداشت‌ها اطلاعات مشتری ننویسید.
- **بررسی زنده پنل** به‌طور پیش‌فرض خاموش است («امنیت و منابع»). در صورت فعال‌کردن، فقط وضعیت سرویس خوانده می‌شود (ورود ادمین و درخواست GET وضعیت)؛ هیچ سرویسی ساخته، تمدید، غیرفعال یا حذف نمی‌شود. فعلاً فقط پنل نوع Marzban پشتیبانی می‌شود و رمز ادمین فقط برای همان اجرا در حافظه نگه داشته می‌شود.

## نسخه 0.5.0 — پنل مقصد RickPanel
پنل اصلی که در میرزا با نوع Marzban ثبت شده، در NEXA از نوع **RickPanel** (نسخه 1.0.0) است. قبل از شروع تبدیل، در بخش «پنل مقصد در NEXA» کد همان پنل (مثلاً از فهرست پنل‌های تبدیل قبلی) را انتخاب کنید، نوع مقصد RickPanel را بزنید و اگر پنل در NEXA از قبل ثبت شده، شناسه (UUID) آن را وارد کنید؛ در غیر این صورت پنل بعداً فقط با تأیید مدیر و از مسیر امن تنظیمات NEXA ساخته و متصل می‌شود.
- شناسه داخلی `rickpanel` و نام `RickPanel` مستقیماً از کد NEXA خوانده شده‌اند و حدس زده نشده‌اند.
- فقط پنل‌های انتخاب‌شده نگاشت می‌شوند؛ سایر پنل‌ها بدون تغییر می‌مانند.
- هیچ اطلاعات مشتری، سرویس، حجم، انقضا یا شناسه قدیمی تغییر نمی‌کند و هیچ سرویسی از نو ساخته نمی‌شود. رمز یا اطلاعات ورود پنل در این برنامه وارد نمی‌شود.
- خط فرمان: `--panel-target CODE=rickpanel,panel_id=UUID,version=1.0.0`

## نسخه 0.6.0 — داده خام مبدأ در بسته (قرارداد 1.4.0)
بسته خروجی اکنون یک «تصویر خام» از جدول‌های `user`، `invoice` و `product` (فقط ستون‌هایی که NEXA می‌خواند) و فهرست ساختار همه جدول‌ها را هم دارد تا Importer موجود NEXA بدون تغییر از روی بسته کار کند.
- ستون‌های حساس (مانند `inbounds`، `proxies`، `user_info`، `uuid`) هرگز در بسته قرار نمی‌گیرند.
- اگر مقدار یکی از این ستون‌ها با نوع ستونش سازگار نباشد (مثلاً `12.5` در ستون عددی صحیح)، ستون باینری باشد یا کلید اصلی تکراری/خالی باشد، بسته مسدود می‌شود و مقدار هرگز حدس زده نمی‌شود.
- این داده‌ها فقط داخل بسته رمزگذاری‌شده هستند.

## آماده‌سازی برای آزمایش واقعی در NEXA (محیط ایزوله)
این بخش برای اولین آزمایش با بکاپ واقعی است. بسته در یک NEXA کاملاً جدا وارد می‌شود (راهنمای `docs/legacy-migration/nxpkg-real-rehearsal.md` در مخزن NEXA). Production و Staging در این آزمایش هیچ نقشی ندارند.

1. **دانلود نسخه:** از Actions مخزن `mirza-to-nexa`، Artifact با نام `Mirza2Nexa-windows-x64-v0.6.0` را دانلود کنید. این فایل از اجرای CI موفق روی شاخهٔ `claude/nxpkg-source-snapshot` ساخته شده است. GitHub برای هر Artifact یک `digest` (SHA-256) نشان می‌دهد. چکیدهٔ فایل ZIP دانلودشده را با این دستور بگیرید و با آن مقایسه کنید:
   ```powershell
   Get-FileHash .\Mirza2Nexa-windows-x64-v0.6.0.zip -Algorithm SHA256
   ```
2. **بررسی سلامت:** دستور `.\Mirza2Nexa.exe selfcheck` باید `"version": "0.6.0"` و `"ok": true` نشان دهد.
3. **تبدیل:**
   - پنل مقصدِ پنل اصلی را **RickPanel** بگذارید.
   - کلید را به‌صورت **فایل کلید** (`.nxkey`) بسازید.
   - پیش از هر کار دیگر، در گزارش برنامه مطمئن شوید هیچ مسدودکننده‌ای (`UNCLASSIFIED_TABLE` یا `COVERAGE_INCOMPLETE`) وجود ندارد. NEXA هر جدولی را که طبقه‌بندی نشده باشد رد می‌کند.
4. **بازبینی مالکیت (اختیاری):** اگر بازبینی دسته‌جمعی مالکیت را انجام می‌دهید، در پایان آن را **مُهر (Seal)** کنید و `ownership-decisions.json` را خروجی بگیرید.
5. **انتقال:** فایل `.nxpkg`، فایل `.nxkey` و (در صورت وجود) فایل تصمیم‌ها را **فقط دستی** به ماشین آزمایش منتقل کنید، مثلاً با فلش. هرگز آن‌ها را از طریق GitHub، ایمیل، پیام‌رسان یا فضای ابری جابه‌جا نکنید.
6. **ثبت اعداد برای مقایسه:** گزارش تطبیق برنامه (`reconciliation.json` و صفحهٔ گزارش) را نگه دارید. این اعداد بعداً با اعداد Dry Run در NEXA و با خروجی `verify` مقایسه می‌شوند.
